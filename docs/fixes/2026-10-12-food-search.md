# 2026-10-12 · 식단 기록 PR B — 음식 검색(공공 영양 DB)

"하림 닭가슴살"을 치면 제품이 나오고, 고르면 먹은 양에 맞춰 칼로리 · 단백질 · 탄수화물 · 지방이 채워진다.
사진 인식(다음 PR C)도 AI 가 찾은 음식 이름을 이 검색에 넣어 영양값을 DB 에서 가져오게 할 예정.

- 추리면서 고친 것(실제 데이터를 보고)

  - "1회 섭취참고량"은 분류별 기준량이라 100g 닭가슴살 한 팩이 30g → 포장 무게(`package_g`)를 따로 두고, 화면 기본 양은 포장이 500 이하면 포장 전체.
  - 음식 DB 는 같은 음식이 급식 · 외식으로 여러 줄 → 이름당 하나(급식이 아닌 것 우선).

## 2. 서버
- `FoodItem`(`food_items`) · `FoodSource`(PROCESSED · DISH · RAW). 사용자 데이터가 아니라 탈퇴 대상 아님.
- `FoodCatalogService`
  - 서버가 뜬 뒤 별도 스레드에서 파일 줄 수 ↔ 표 줄 수 비교, 다르면 한 트랜잭션으로 지우고 다시 넣음(넣는 동안은 이전 데이터로 검색). 여러 줄을 insert 한 문장(500줄)으로 — 운영 접속 주소에 대량 넣기 옵션이 없어도 빠르게. 로컬 MySQL 약 1~2분.
  - 검색: 검색어를 낱말로 나눠 각 낱말이 `search_key`(이름 + 업체, 소문자, 글자 · 숫자만)에 모두 들어 있는 것 → 이름 길이순 300개 → 순위(이름이 검색어와 같음 > 검색어로 시작 > 첫 낱말로 시작 > 그 밖, 한 낱말이면 원재료 > 음식 > 제품, 원재료는 쉼표 앞 이름으로도 비교) → 30개.
  - 비슷한 말: 계란↔달걀, 닭가슴살→닭고기가슴살, 소고기↔쇠고기(원재료 DB 의 이름).
  - 처음 넣는 동안은 `ready:false` → 화면이 "준비 중" 안내.
- `GET /api/diet/foods?q=`(로그인 필요, 40자까지).
- Postgres 인덱스: `db/migration/postgresql/V5__food_search_index.sql` — `pg_trgm` + GIN. 확장을 만들 권한이 없으면 건너뜀(서버는 뜬다). MySQL `V5` 는 번호만 맞춘 빈 이전.
  - 측정(임시 PG17, 32만 줄): 인덱스 없이 약 150ms(한 글자 530ms) → 인덱스 있으면 3글자 이상 1ms 안쪽.
- 테스트는 `food.catalog.autoload=false`(30만 줄을 매번 넣지 않게), `FoodSearchTest` 가 작은 파일로 넣기 · 검색을 확인.

## 5. 남은 것
- 운영 첫 배포 뒤 몇 분은 검색이 "준비 중"(데이터 넣는 중). Railway 로그에서 "음식 검색 데이터 …건을 넣었습니다" 확인.
- 저장소에 7MB 데이터 파일이 들어간다. 판이 바뀔 때마다 7MB 씩 늘어나므로 자주 갱신하지 않는다(분기 1회 정도).
- 로컬 MySQL 은 인덱스가 없어 한 번 검색에 0.5~0.7초.
