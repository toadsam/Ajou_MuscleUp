# AI 와 함께 개발한 방식 — 득근득근

> 이 문서는 "AI 를 활용해 개발했다"는 말의 근거를 모아 둔 것이다.
> 무엇을 AI(Claude Code)에게 맡겼고, 무엇을 내가 정했고, 결과를 어떻게 믿을 수 있게 만들었는지를 적는다.
> `✍️` 표시는 내 말로 직접 채울 칸이다.

---

## 1. 한 줄 요약

AI 에게 코드를 "짜 달라"고 맡기는 데서 멈추지 않았다. **AI 가 따라야 할 작업 규칙 · 자동 검증 · 기록 강제 장치(하네스)** 를 만들었다.
그 위에서 제품 방향은 내가 정하고, 구현은 AI 와 PR 단위로 나눠 진행했다. merge 할 때마다 운영 서버에서 확인했다.

---

## 2. 역할 나누기

| 누가 | 한 일 |
|---|---|
| **나** | 제품 방향(동아리 앱 → 모든 운동 모임 · 헬스장으로 확장), 서비스 이름("득근득근"), 기능 범위(예: 공동구매는 "같은 모임 안" + "전체 공개" 둘 다), 디자인 방향(짐 플로어 v2) 선택, 위험한 작업 승인(커밋 · push · 삭제), PR merge, 계정 · 비밀값 관리(Google 로그인, 카카오 콘솔, 배포 환경변수) |
| **AI** | 코드 조사, 설계 초안, 구현, 테스트 작성, 검증 실행, 화면 확인, 기록 작성 |
| **둘이 같이** | 설계 문서 검토(`docs/vision.md`, `docs/design/stage0-gyms.md`), PR 을 어떻게 나눌지, merge 후 운영 확인 |

**AI 에게 절대 맡기지 않은 것**
- 계정 정보 입력, 비밀값 출력
- 되돌리기 어려운 작업을 묻지 않고 실행하는 것: 강제 push, 파일/브랜치 삭제, reset

이 규칙은 [CLAUDE.md](../CLAUDE.md) 에 적어 두고 AI 가 매번 읽게 했다.

✍️ *내가 직접 내린 결정 중 가장 중요했던 것 1~2개와 그 이유:*

## 3. 하네스 — AI 결과물을 믿을 수 있게 만든 장치

AI 는 빠르지만 같은 실수를 반복하고, 확인하지 않은 것을 "됐다"고 말할 수 있다. 그래서 장치 네 가지를 만들었다.

| 장치 | 하는 일 | 파일 |
|---|---|---|
| **작업 규칙** | 원인 증명 → 수정 → 검증 → 화면 확인(데스크톱 + 375px) → 기록. 디자인 금지 규칙, 알려진 함정 목록 | [CLAUDE.md](../CLAUDE.md) |
| **자동 검증** | 타입 검사 0 오류, 린트는 "바꾸기 전보다 늘지 않았는지" 비교, 빌드 | [scripts/verify.sh](../scripts/verify.sh) |
| **기록 강제** | 코드가 수정 기록보다 새것이면 AI 가 작업을 끝내지 못하게 막는다(Stop 훅) | [.claude/hooks/require-fix-log.sh](../.claude/hooks/require-fix-log.sh) |
| **수정 기록** | 수정마다 불편 → 원인(근거) → 고친 방법 → 확인한 것 / **못 한 것** | [docs/fix-log.md](fix-log.md), [docs/fixes/](fixes/README.md) |

**함정 목록은 실제 사고에서 쌓였다.** 한 번 겪은 문제를 CLAUDE.md 에 적으면 다음 세션의 AI 도 같은 문제를 피한다.
- 로컬에선 통과했는데 Vercel 에서만 빌드 실패: 상위 폴더 `@types` 를 TypeScript 가 끌어옴
- 앱 안 미리보기 브라우저가 캐시를 비워서, 서비스 워커 시험 결과가 실제보다 좋게 나옴
- DB enum 칸에 새 값을 넣으면 저장이 실패함: Hibernate 가 만든 CHECK 제약
- 이 PC 의 환경변수 때문에 백엔드가 잘못된 DB 설정으로 뜸

## 5. AI 가 틀렸던 사례와 잡아낸 방법

AI 를 썼다는 말보다 **AI 가 틀린 걸 어떻게 잡았는지**가 더 중요하다고 본다.

| 사례 | 어떻게 잡았나 |
|---|---|
| 하위 에이전트가 만든 가입 화면이 서버 응답을 `REQUESTED` 로 기다렸다. 서버는 실제로 `PENDING` 을 보낸다. 그대로 두면 신청해도 안내가 안 뜬다 | 메인 세션이 서버 코드와 화면 코드를 대조하며 검토 |
| 설계 조사에서 "모임 상세 API 가 외부에 노출돼 있다"고 판단했다. 실제로는 이미 막혀 있었다 | 코드를 다시 확인하고 설계 문서를 정정 |
| 로컬 타입 검사는 통과했는데 Vercel 빌드가 실패했다 | `tsc --explainFiles` 로 원인(상위 폴더 타입)을 증명하고 설정을 고정 |
| 서비스 워커 수정이 "잘 된다"고 나왔지만, 시험 환경이 캐시를 비우고 있었다 | 실제 Chrome 에서 빌드본으로 다시 시험 → 함정 목록에 추가 |
| Flyway 자동 설정을 끈 줄 알았는데 테스트 설정이 덮어써서 계속 돌았다 | 테스트 실패 로그에서 추적, 코드에서 직접 제외 |
| Postgres 에서만 검색이 깨졌다(`lower(bytea)`) | 임시 Postgres 를 띄워 운영과 같은 DB 로 테스트 |

## 6. 내가 설명할 수 있는 핵심 결정

✍️ *각 항목을 내 말로 2~3줄씩 설명해 두기. 면접에서 가장 많이 물어볼 부분이다.*

1. **배포 직후 예전 화면이 뜬 이유와 해결**
   - 핵심: 서비스 워커가 옛 `index.html` 을 계속 내줬다 → 화면 HTML 은 네트워크를 먼저 보게(NetworkFirst) 바꿨다. 조각 파일을 못 받으면 한 번 새로고침한다.
   - ✍️
2. **소셜 계정을 이메일이 아니라 공급자 고유 번호로 연결한 이유**
   - 핵심: 이메일은 바뀌거나 없을 수 있다(카카오). 인증되지 않은 이메일로 기존 계정에 붙이면 남의 계정을 가로챌 수 있다.
   - ✍️
3. **Flyway 를 Hibernate 다음에 돌리는 이유**
   - 핵심: 테이블은 Hibernate(ddl-auto)가 만들고, Flyway 는 데이터 옮기기만 맡긴다. 그러면 기존 운영 DB 를 그대로 두고 도입할 수 있다.
   - ✍️
4. **권한 검사를 `GymPermissionService` 한 곳에 모은 이유**
   - 핵심: 동아리 · 모임 · 헬스장 · PT 가 같은 구조라 역할(모임장 · 운영진 · 멤버) 규칙을 한 곳에서 바꿔야 빠짐이 없다.
   - ✍️

## 7. 배운 것 / 한계

- AI 는 "확인하지 않은 것"을 숨기기 쉽다 → 기록 양식에 **"아직 못 한 것"** 칸을 필수로 넣었다.
  - 예: 로그인이 필요한 화면은 아직 직접 확인하지 못한 부분이 남아 있다.
- 범위를 크게 맡기면 리뷰가 어려워진다 → 설계 문서를 먼저 쓰고 PR 을 작게 나눴다.
