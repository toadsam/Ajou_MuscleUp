왜 파일만 지우면 안 되나

git은 모든 과거를 기억합니다. 비밀번호가 든 파일을 커밋한 뒤 다음 커밋에서 지워도, git log로 과거 버전을 꺼내면 그대로 나옵니다. 그래서 진짜로 없애려면 히스토리 자체를 다시 써야 하고, 그게 이날 벌어진 일입니다.

그리고 이게 지금 .gitignore가 제대로 되어 있는 이유입니다. {{s7}}장에서 "비밀 관리가 잘 되어 있다"고 했는데, 그건 처음부터 잘한 게 아니라 한 번 크게 데인 뒤에 고친 것입니다. 코드만 봐서는 절대 알 수 없는 사실이죠.

참고로 한 번 GitHub에 올라간 비밀은 유출된 것으로 간주하고 무조건 교체해야 합니다. 히스토리를 지워도 누군가 이미 클론했거나 봇이 수집했을 수 있으니까요. 그때 키를 실제로 새로 발급했는지는 커밋만으로는 알 수 없습니다 — 기억을 되짚어볼 만한 지점입니다.

01 — 큰 그림

이건 앱 하나가 아니라, 따로 도는 프로그램 셋입니다

가장 먼저 잡아야 할 개념입니다. npm run dev 한 번으로 전부 뜨지 않습니다. 서로 다른 세 개의 프로그램이 각자 다른 포트에서 돌고, 네트워크로 대화합니다. 이걸 모르면 "왜 로그인이 안 되지?"의 원인을 영원히 못 찾습니다 — 셋 중 어느 놈이 안 떴는지부터 봐야 하거든요.

frontend · :5173

브라우저에서 도는 화면. React 19 + TypeScript + Vite. 사용자에게 보이는 전부이지만 스스로는 아무 데이터도 갖고 있지 않습니다.

backend · :8080

Spring Boot 3.5 REST API. 진짜 데이터와 진짜 규칙이 사는 곳. 로그인 검증, DB 읽기·쓰기, 권한 판단, OpenAI 호출이 전부 여기서 일어납니다.

realtime · :4001

Node.js + Socket.IO. 라운지에서 캐릭터가 1초에 수십 번 움직이는 것처럼, 너무 자주 바뀌어서 DB에 넣기 아까운 상태만 담당합니다.

왜 실시간만 따로 뗐을까

핵심은 데이터의 수명입니다. 출석 기록은 1년 뒤에도 남아 있어야 하니까 DB에 넣습니다. 그런데 "지금 이 사람이 좌표 (843, 219)에 서 있다"는 정보는 0.06초 뒤면 쓸모가 없습니다.

그래서 라운지 상태는 realtime/src/rooms.ts:7의 자바스크립트 Map 하나에만 삽니다. 서버를 껐다 켜면 전부 사라집니다 — 그리고 그래도 괜찮습니다. 그게 의도한 설계니까요.

대신 치른 대가

상태가 한 프로세스의 메모리에만 있으므로, realtime 서버를 2대로 늘리면 라운지가 쪼개집니다. 1번 서버에 붙은 사람과 2번 서버에 붙은 사람은 서로를 못 봅니다. 늘리려면 Redis 같은 공용 저장소가 필요해집니다. 이건 실수가 아니라 지금은 안 하기로 한 선택입니다.

02 — 파일 구조

백엔드 폴더 8개는 "층"입니다

backend/src/main/java/com/ajou/muscleup/ 안의 폴더들은 기능별 분류가 아니라 책임의 층(layer)입니다. 각 층은 자기 아래층만 부를 수 있고 위로는 올라가지 않습니다. 이 한 방향 규칙이 지켜지는 동안은 파일이 아무리 늘어도 구조가 안 무너집니다.

레이어 탐색기 254 files

DTO와 Entity를 왜 굳이 둘 다 만들까

파일이 가장 많은 두 폴더입니다 (dto 92개, entity 46개). "같은 데이터인데 왜 두 번 쓰지?" 싶지만 이유는 딱 하나로 설명됩니다.

entity/User.java:27 에는 이 줄이 있습니다.

@Column(nullable = false)
private String password;   // BCrypt 해시

그런데 dto/UserDTO.java 에는 password가 없습니다.

public static UserDTO from(User u) {
    return UserDTO.builder()
            .id(u.getId()).name(u.getName())
            .email(u.getEmail()).nickname(u.getNickname())
            .role(u.getRole())
            .build();          // password는 의도적으로 뺌
}

그래서 결론

Entity는 DB의 모양, DTO는 바깥에 보여줄 모양입니다. Entity를 그대로 응답에 실으면 비밀번호 해시가 브라우저로 날아갑니다. DTO라는 한 겹이 그걸 막는 체 역할을 합니다. 파일 92개가 귀찮아 보여도, 그 92개가 전부 "밖에 나가도 되는 것만 고르는" 필터입니다.

이 그래프를 읽는 법

이건 단순한 그림이 아니라 "여기 고치면 어디가 깨지나"의 지도입니다. 실무에서 가장 중요한 감각이고, 코드를 아무리 오래 읽어도 이걸 그려보지 않으면 안 생깁니다.

캐릭터 점수는 어떤 공식으로 나오나

이 프로젝트의 심장입니다. CharacterServiceImpl.java:196의 evaluateStats()가 인바디 수치와 3대 중량을 100점 만점 점수로 바꾸고, 그 점수에서 레벨·티어·진화단계·칭호가 전부 파생됩니다.

아래 계산기는 코드의 공식을 그대로 옮긴 것입니다. 슬라이더를 움직이면 실제 서버가 계산하는 것과 같은 값이 나옵니다.

캐릭터 점수 계산기 CharacterServiceImpl.java:196–255 재현

100점이 어떻게 쪼개져 있나

점수는 다섯 조각의 합입니다. 각 조각의 최대치가 그 항목을 얼마나 중요하게 보는지를 그대로 드러냅니다.

항목만점공식의미
3대 절대중량55min(총합 / 700, 1) × 55남 700kg · 여 420kg이 만점
체중 대비 근력20min(총합÷체중 / 3.5, 1) × 20남 3.5배 · 여 3.0배가 만점
키 보정 근육량1515 − |SMI − 10.8| × 2.1SMI = 골격근kg ÷ 키m²
BMI 적합도66 − |BMI − 23| × 0.9목표에서 멀수록 감점
체지방 적합도44 − |체지방% − 15| × 0.22목표에서 멀수록 감점
출석 보너스8min(출석포인트 × 0.4, 8)위 100점에 더해진 뒤 100으로 잘림

숫자는 전부 CharacterServiceImpl.java:342–374에서 그대로 가져왔습니다. 성별에 따라 기준값이 다릅니다 (여성은 3대 420kg, BMI 21, 체지방 24%, SMI 8.7).

여기서 가장 중요한 발견

출석 보너스의 상한은 8점입니다. 3대 중량은 55점이고요. 코드에도 이렇게 적혀 있습니다 — CharacterServiceImpl.java:430: 

// Attendance helps, but should not override physical metrics.
return clamp(attendancePoints * 0.4, 0.0, 8.0);

즉 출석만 열심히 해도 캐릭터는 거의 안 자랍니다. 매일 출석해서 20포인트를 모아도 8점에서 잘리고, 그 이상은 아무리 쌓아도 소용없습니다. 캐릭터를 키우는 진짜 방법은 인바디를 다시 재고 3대 중량을 갱신하는 것입니다.

이건 버그가 아니라 설계상의 긴장입니다. 서비스의 표면적 약속은 "매일 출석하면 캐릭터가 큰다"인데, 실제 점수 배분은 출석 8% : 신체능력 92%입니다. 어느 쪽이 옳다는 게 아니라, 이 불일치를 알고 있어야 "왜 매일 출석하는데 레벨이 그대로냐"는 질문에 답할 수 있습니다.

티어는 점수만으로 정해지지 않습니다

레벨은 단순합니다 — 레벨 = 1 + floor(총점). 진화단계도 (레벨−1) ÷ 10으로 0~9단계입니다. 그런데 티어는 특이합니다. 점수 기준 티어와 3대 중량 기준 티어를 따로 구한 뒤 섞습니다. 

// CharacterServiceImpl.java:297
private CharacterTier blendLiftAndScoreTier(CharacterTier liftTier, CharacterTier scoreTier) {
    int liftIndex  = tierIndex(liftTier);
    int scoreIndex = tierIndex(scoreTier);

    if (scoreIndex >= liftIndex + 2) return tierByIndex(min(7, liftIndex + 1));
    if (scoreIndex <= liftIndex - 2) return tierByIndex(max(0, liftIndex - 1));
    return liftTier;   // 기본은 3대 중량 티어를 따름
}

읽어보면 3대 중량 티어가 기준이고, 종합 점수는 ±1단계만 보정합니다. 점수가 아무리 높아도 3대가 약하면 티어가 크게 오르지 않습니다. "티어는 힘으로 정한다"는 게 이 게임의 철학인 셈입니다.

칭호 이름 두 개가 이상합니다

CharacterServiceImpl.java:381의 칭호 목록에서 7단계는 "에포스 에시언트", 9단계는 "어의너"입니다. 나머지("초보 헬린이", "루틴 입문자", "레전드 파워러")는 자연스러운데 이 둘만 뜻을 알 수 없는 말입니다. AI가 만들어낸 이름이 그대로 남은 것으로 보입니다. 최고 등급 칭호라 사용자 눈에 가장 많이 띄는 자리인데도요. 고치기는 제일 쉬운 축입니다.

06 — AI

인바디 사진 한 장이 상담 리포트가 되기까지

service/AiService.java는 895줄로 이 프로젝트에서 가장 긴 백엔드 파일입니다. 그런데 그중 OpenAI를 실제로 부르는 코드는 30줄도 안 됩니다. 나머지 800여 줄은 전부 "AI가 거짓말했을 때 어떻게 알아채고 고칠 것인가"에 쓰였습니다. 이게 이 프로젝트에서 기술적으로 가장 성숙한 부분입니다.

문제: AI는 사진을 잘못 읽습니다

인바디 용지를 찍은 사진을 AI에게 주고 "숫자를 읽어줘"라고 하면, 대체로 잘하지만 가끔 틀립니다. 체지방량을 골격근량으로 착각하거나, 소수점을 놓치거나, 아예 없는 값을 지어냅니다. 그대로 믿고 상담 리포트를 만들면 엉터리 조언이 사용자에게 갑니다.

1단계 — 자유 서술 대신 정해진 틀을 강제

AiService.java:405에서 response_format에 JSON 스키마를 넣습니다. 이러면 AI가 마음대로 문장을 쓰지 못하고 지정된 필드만 채워서 돌려줍니다. 

root.set("response_format", buildInbodyJsonSchemaFormat());

덤으로 이미지는 base64로 인코딩해 data: URL로 실어 보냅니다 — 파일을 어딘가 올려두고 링크를 주는 게 아니라 요청 본문에 직접 담습니다. 그래서 인바디 사진이 외부에 남지 않습니다.

2단계 — 결과에 점수를 매깁니다

AiService.java:795의 qualityScore()가 AI 응답을 채점합니다. 사람이 보는 게 아니라 코드가 규칙으로 판정합니다. 

int score = 20;
score += corePresent * 15;                    // 핵심 수치가 있으면 가산
if (bmi != null) score += 3;
if (weeklyCheckpoints.size() >= 4) score += 6;

// 말이 안 되는 값이면 크게 감점
if (skeletal > weight) score -= 25;           // 근육이 체중보다 무겁다?

double diff = abs((weight * bodyFatPercent / 100.0) - bodyFatKg);
if (diff > 3.0) score -= 20;                  // 체지방 %와 kg이 안 맞는다
else if (diff > 1.5) score -= 10;

핵심은 마지막 두 검사입니다. 체지방률과 체지방량은 서로 계산이 되어야 합니다 — 체중 70kg에 체지방 20%면 체지방량은 14kg이어야죠. AI가 읽은 두 값이 서로 안 맞으면 둘 중 하나는 잘못 읽은 것입니다. 정답을 몰라도 모순은 잡아낼 수 있습니다.

3단계 — 점수가 낮으면 다시 물어봅니다

AiService.java:114–133:

Map<String,Object> first = requestInbodyConsultationInternal(..., false);
int firstScore = qualityScore(first);
if (firstScore >= 72) return first;          // 충분히 좋으면 그대로

// 아니면 temperature를 0.2 → 0.1로 낮추고 재시도
Map<String,Object> retry = requestInbodyConsultationInternal(..., true);

if (retryScore > firstScore) {
    warnings.add("초기 추출 정확도가 낮아 재분석한 결과를 사용했습니다.");
    return retry;
}
return first;                                 // 재시도가 더 나쁘면 원본 유지

왜 temperature를 낮추나

temperature는 AI의 "창의성" 손잡이입니다. 높으면 다양하게, 낮으면 보수적·일관되게 답합니다. 숫자를 정확히 읽어야 하는 작업에는 창의성이 독이므로, 재시도할 땐 0.1로 낮춰 확실한 답만 나오게 유도합니다. 그리고 재시도 결과가 더 나쁘면 버립니다 — 재시도했다는 이유만으로 채택하지 않는 게 중요합니다.

4단계 — 빠진 값은 직접 계산해서 채웁니다

AiService.java:700의 applyDerivedMetrics()는 AI가 못 읽은 값을 다른 값에서 유도합니다. 그리고 유도했다는 사실을 사용자에게 알립니다.

마지막 줄이 특히 좋습니다. 확실히 틀린 값은 그냥 지웁니다. 틀린 숫자를 보여주는 것보다 빈칸이 낫다는 판단이죠.

이걸 한 문장으로 말한다면

"AI를 믿지 않는 코드"입니다. 부르고 → 채점하고 → 못 미더우면 다시 묻고 → 모순을 검사하고 → 빈칸을 유도하고 → 못 고칠 값은 버리고 → 사용자에게 경고를 붙여 보냅니다. AI 기능을 붙였다고 말하는 프로젝트는 많지만, 여기까지 하는 경우는 드뭅니다. 면접이나 발표에서 설명할 만한 부분입니다.

09 — 기초

보안, 아무것도 모른다고 치고 처음부터

이 장은 사전 지식을 하나도 가정하지 않습니다. 웹이 왜 애초에 위험한지에서 출발해서, 비밀번호 → 출입증 → 그걸 어디에 둘까 → 공격당하면 어떻게 되나 순서로 쌓아 올립니다. 여기를 이해하면 다음 장의 코드가 전부 "아, 그래서 저렇게 짰구나"로 읽힙니다.

출발점: 서버는 당신을 기억하지 못합니다

웹의 근본 구조부터 봅시다. 브라우저가 서버에 요청을 보내면 서버가 답을 주고, 그걸로 관계가 끝납니다. 다음 요청은 완전히 새로운 손님입니다. 이걸 무상태(stateless)라고 합니다.

그래서 이런 일이 벌어집니다. 

브라우저: "로그인할게요. 아이디 jaehun, 비번 1234"
서버   : "확인했습니다. 환영합니다!"

브라우저: "제 출석 기록 주세요"
서버   : "...누구세요?"        ← 방금 로그인한 걸 기억 못 함

그럼 매 요청마다 아이디·비밀번호를 같이 보내면 되지 않을까요? 안 됩니다. 비밀번호가 네트워크를 수백 번 오가면 그만큼 새어나갈 기회가 늘고, 브라우저가 비밀번호를 계속 들고 있어야 하니까요.

그래서 나온 방법이 출입증입니다. 로그인할 때 딱 한 번 비밀번호를 확인하고, 대신 "이 사람은 jaehun이 맞다"는 증명서를 발급해 줍니다. 이후에는 그 증명서만 보여주면 됩니다. 놀이공원에서 입장할 때 표를 내고 손목 팔찌를 받는 것과 똑같습니다.

그런데 여기서 진짜 문제가 시작됩니다

브라우저는 사용자의 컴퓨터에서 돕니다. 사용자가 F12를 눌러 개발자도구를 열면 자바스크립트 코드도, 저장된 값도 전부 보이고 고칠 수 있습니다.

그러니까 브라우저가 "저는 관리자예요"라고 말해도 서버는 그 말을 믿으면 안 됩니다. 누구나 그렇게 말하도록 고칠 수 있으니까요. 이게 웹 보안의 제1원칙입니다:

클라이언트에서 온 것은 아무것도 믿지 않는다.

이 문장 하나가 이 프로젝트 보안 코드의 전부를 설명합니다. 지금부터 나올 모든 장치는 결국 "그럼 뭘 믿을 수 있게 만들까"의 답입니다.

1단계 — 비밀번호를 어떻게 보관할까

순진한 방법
DB에 비밀번호를 그대로 저장한다

가장 단순합니다. users 테이블에 password: "1234"라고 적어두고, 로그인할 때 입력값과 비교하면 끝이죠.

문제: DB가 한 번 유출되면 전원의 비밀번호가 평문으로 넘어갑니다. 게다가 사람들은 같은 비밀번호를 여러 사이트에 쓰기 때문에, 우리 서비스가 털리면 그 사람의 은행 계정까지 위험해집니다. 개발자 본인도 남의 비밀번호를 볼 수 있고요.

해결
되돌릴 수 없게 뭉개서 저장한다 — 해시

해시는 어떤 값을 고정된 길이의 뒤죽박죽 문자열로 바꾸는 계산입니다. 핵심은 한 방향으로만 간다는 것입니다. 

"1234"  →  해시  →  "$2a$10$N9qo8uLOickgx2ZMRZo..."
                     ↑
              이걸로 "1234"를 되찾는 건 불가능

그럼 로그인은 어떻게 확인할까요? 비교 방향을 바꿉니다. 저장된 해시를 원래대로 되돌리는 게 아니라, 입력받은 비밀번호를 똑같이 해시해서 결과가 같은지 봅니다. 

// UserService.login() 안에서 실제로 하는 일
passwordEncoder.matches(입력받은비번, DB에저장된해시)
// → 입력값을 해시해서 저장된 해시와 같은지 비교

이제 DB가 통째로 털려도 공격자가 얻는 건 뭉개진 문자열뿐입니다.

그런데 아직 부족합니다
공격자는 미리 계산해둘 수 있다

해시는 같은 입력이면 항상 같은 결과가 나옵니다. 그래서 공격자는 흔한 비밀번호 수백만 개를 미리 해시해서 표로 만들어 둡니다. 털어온 해시를 그 표에서 찾아보면 원래 비밀번호가 바로 나옵니다.

게다가 컴퓨터는 빠릅니다. 일반적인 해시 함수는 초당 수십억 번 계산할 수 있어서, 그냥 무작정 다 넣어보는 것도 가능합니다.

그래서 BCrypt
소금을 치고, 일부러 느리게 만든다

이 프로젝트가 쓰는 BCryptPasswordEncoder는 두 가지를 더 합니다.

① 소금(salt) 뿌리기 — 비밀번호마다 무작위 값을 섞어서 해시합니다. 그래서 두 사람이 똑같이 "1234"를 써도 저장된 해시는 서로 다릅니다. 미리 만들어둔 표가 통째로 무용지물이 되죠. (소금값은 해시 문자열 안에 같이 들어갑니다.)

② 일부러 느리게 — BCrypt는 계산을 수천 번 반복하도록 설계됐습니다. 정상 로그인 한 번은 0.1초쯤 걸려서 사람은 못 느낍니다. 그런데 공격자가 10억 개를 대입하려면 수십 년이 걸립니다.

느린 게 기능인 거의 유일한 경우입니다. 코드에는 딱 한 줄로 끝납니다 — SecurityConfig.java:33의 return new BCryptPasswordEncoder();

2단계 — 출입증을 위조할 수 없게 만들기

비밀번호는 안전해졌습니다. 이제 로그인에 성공한 사람에게 줄 출입증을 만들 차례입니다.

가장 단순한 출입증은 "jaehun@ajou.ac.kr, USER"라고 적힌 쪽지겠죠. 그런데 아까 제1원칙을 떠올려 보세요. 사용자가 이 쪽지를 "jaehun@ajou.ac.kr, ADMIN"으로 고쳐서 보내면? 서버는 구별할 방법이 없습니다.

그래서 서명이 필요합니다. 서버만 아는 비밀 열쇠로 내용에 도장을 찍는 겁니다. 내용이 한 글자라도 바뀌면 도장이 안 맞게 됩니다. 이렇게 만든 출입증이 JWT입니다.

말로만 하면 감이 안 오니 진짜 토큰을 직접 뜯어봅시다. 아래는 이 프로젝트의 JwtUtil.java:35가 만드는 것과 똑같은 구조의 토큰입니다.

JWT 해부기

가장 많이 오해하는 것

토큰은 암호화되어 있지 않습니다. 가운데 부분은 그냥 Base64라는 인코딩일 뿐이라, 누구나 1초 만에 풀어서 읽을 수 있습니다. 위 탭에서 직접 보셨듯이요.

그러니까 JWT에 비밀번호나 주민번호 같은 걸 넣으면 절대 안 됩니다. 서명이 보장하는 건 "내용이 바뀌지 않았다"이지 "내용이 안 보인다"가 아닙니다. 이 둘은 완전히 다른 이야기입니다.

이 프로젝트는 이메일·역할·타입·시각만 넣었습니다 — 남이 봐도 괜찮은 것들이죠. 올바른 선택입니다.

왜 출입증을 두 장이나 줄까

로그인하면 토큰을 두 개 받습니다. 처음 보면 이유를 모르겠는데, 서로 반대되는 두 요구 사이의 타협입니다.

짧아야 하는 이유

토큰을 도둑맞으면 도둑이 나인 척할 수 있습니다. 수명이 짧을수록 피해가 작습니다. → 15분짜리가 좋겠네

길어야 하는 이유

토큰이 만료되면 다시 로그인해야 합니다. 15분마다 로그인하라면 아무도 안 씁니다. → 90일짜리가 좋겠네

답은 역할을 나누는 것입니다.

토큰수명역할비유
access token15분 API를 부를 때마다 제시하는 출입증. 자주 쓰이니 자주 노출됨 → 짧게. 놀이기구 탈 때 보여주는 손목 팔찌
refresh token90일 access가 만료됐을 때 새로 받아오는 용도로만 씀. 거의 안 꺼내니 덜 노출됨 → 길게. 팔찌를 새로 받을 수 있는 영수증

그래서 15분마다 access가 만료되면, 프론트엔드가 사용자 몰래 refresh를 내밀어 새 access를 받아옵니다. 사용자는 90일 동안 로그인 화면을 다시 볼 일이 없죠. installFetchAuth.ts가 하는 일이 정확히 이것입니다.

그리고 이 프로젝트는 refresh token만 DB에 저장합니다 (refresh_tokens 테이블). 왜냐면 JWT는 한 번 발급하면 취소할 수가 없기 때문입니다. 최소한 재발급만은 끊을 수 있게 하려고 DB에 기록을 남기는 겁니다 — 로그아웃할 때 revokeAllByUserEmail()이 그걸 지웁니다.

3단계 — 출입증을 어디에 보관할까

토큰을 받았습니다. 브라우저 어딘가에 저장해야 다음 요청에 쓸 수 있죠. 그런데 어디에 두느냐가 보안을 좌우합니다. 선택지는 둘입니다.

localStorage

브라우저가 제공하는 저장소. localStorage.getItem("user")로 꺼냅니다.

장점: 다루기 쉽고, 헤더에 직접 붙일 수 있음
치명적 단점: 자바스크립트로 읽힙니다

httpOnly 쿠키

서버가 Set-Cookie로 심어주고, 브라우저가 요청마다 자동으로 붙여 보냅니다.

장점: httpOnly 옵션이 붙으면 자바스크립트가 못 읽습니다
단점: 다루기가 조금 번거로움

파일 업로드 — 경로 탈출은 막혀 있습니다

파일 업로드는 웹에서 가장 사고가 잦은 기능입니다. 공격자가 파일명에 ../../../etc/passwd 같은 걸 넣어 서버의 아무 파일이나 읽거나 덮어쓰는 공격을 경로 탈출이라고 합니다.

FileController.java는 이걸 세 겹으로 막고 있습니다.

// 1. 폴더명에서 위험한 문자 제거 (:259)

세 번째가 핵심입니다. normalize()로 ..를 실제로 계산해 없앤 뒤, 그 결과가 업로드 루트 아래인지 다시 확인합니다. 문자열 필터만 믿지 않고 최종 경로를 검증하는 게 정석이고, 여기선 그렇게 되어 있습니다.

다만 업로드된 파일 자체는 공개입니다

SecurityConfig.java:79에서 GET /api/files/proxy가 permitAll입니다. 즉 URL만 알면 로그인 없이 누구나 파일을 볼 수 있습니다. 파일명이 UUID라 추측은 사실상 불가능하지만, 이건 "권한으로 막은 것"이 아니라 "주소를 모르게 한 것"입니다. 인바디 사진처럼 민감한 이미지가 여기에 올라간다면 링크가 한 번 새는 순간 되돌릴 수 없습니다. 공유 기능을 위한 의도적 선택으로 보이지만, 알고 쓰는 것과 모르고 쓰는 것은 다릅니다.

CSRF를 꺼둔 게 왜 괜찮은가 (그리고 언제 안 괜찮아지나)

SecurityConfig.java:58에 .csrf(csrf -> csrf.disable())이 있습니다. 쿠키로 인증하는데 CSRF를 끄는 건 보통 위험 신호입니다. 그런데 이 경우엔 방어가 다른 데 있습니다.

쿠키가 전부 SameSite=Lax로 설정돼 있습니다 (AuthController.java:232). Lax는 다른 사이트에서 오는 POST 요청에 쿠키를 붙이지 않습니다. 그래서 악성 사이트가 몰래 POST /api/attendance/today를 보내도 인증이 안 됩니다.

단, 이 전제가 깨지는 조건

SameSite를 None으로 바꾸는 순간(예: 다른 도메인에 프론트를 올리려고) 이 방어가 통째로 사라집니다. application-prod.properties에서 APP_COOKIE_SAME_SITE 환경변수로 바꿀 수 있게 되어 있으니, 언젠가 누군가 이걸 바꾸면 CSRF 구멍이 열립니다. 지금은 안전하지만 조건부로 안전합니다.

테이블 모양은 누가 정하나 — 두 개의 정답이 공존합니다

이 프로젝트에는 DB 스키마를 만드는 방법이 두 가지가 동시에 돌고 있습니다.

  • 자동: spring.jpa.hibernate.ddl-auto=update — Entity 클래스를 보고 Hibernate가 알아서 테이블을 만들고 컬럼을 추가합니다.
  • 수동: backend/sql/에 마이그레이션 SQL 12개.

파일명을 보면 개발 흐름이 그대로 보입니다 — migration_20260308_workout_crew.sql(크루 기능), migration_20260315_attendance_media_share.sql(사진 공유), migration_20260324_character_resting.sql(휴식 모드). 기능이 추가된 순서와 날짜가 남아 있는 셈입니다.

왜 이게 애매한가

ddl-auto=update는 컬럼을 추가할 순 있어도 이름을 바꾸거나 지우지는 못합니다. 그래서 그런 변경이 필요할 때마다 손으로 SQL을 쓴 흔적이 12개 쌓인 겁니다. 문제는 "지금 운영 DB가 정확히 어떤 모양인지" 알려면 두 군데를 다 봐야 한다는 것. 혼자 개발할 땐 굴러가지만, 팀이 되거나 서버가 늘면 여기서 사고가 납니다.

제대로 하려면 Flyway나 Liquibase로 SQL 마이그레이션을 유일한 정답으로 만들고, ddl-auto는 validate로 낮춥니다. 그러면 Entity와 실제 DB가 어긋났을 때 서버가 조용히 넘어가지 않고 부팅에 실패해서 바로 알려줍니다.

PostgreSQL 응급처치 코드가 있습니다

config/PostgresSchemaRepairRunner.java라는 파일이 있습니다. 이름 그대로 부팅할 때 스키마를 손보는 코드입니다. 로컬은 MySQL, 배포는 PostgreSQL을 쓰다 보니 둘 사이 타입이 안 맞는 문제가 생겼고, 그걸 앱 시작 시점에 고치는 방식으로 때운 흔적입니다. 이런 파일이 존재한다는 것 자체가 위의 마이그레이션 문제가 이미 한 번 터졌다는 증거입니다.

마지막 줄이 빈틈입니다

GlobalExceptionHandler는 ResponseStatusException과 MethodArgumentNotValidException 두 가지만 잡습니다. NullPointerException이나 DB 제약 위반 같은 예상 못 한 예외는 통과해서 Spring 기본 에러 페이지가 나갑니다. 그러면 응답 모양이 ApiErrorResponse와 달라서, 프론트가 error.message를 읽으려다 undefined를 만납니다.

고치는 법: @ExceptionHandler(Exception.class)를 하나 더 추가해서 나머지 전부를 500 + 같은 JSON 형태로 감쌉니다. 이때 스택트레이스는 로그에만 남기고 사용자에겐 보내지 않는 것이 중요합니다 — 내부 구조가 그대로 노출되니까요.

401과 403의 차이 — 헷갈리면 디버깅이 안 됩니다

이 둘을 구분하는 게 인증 문제 해결의 절반입니다.

  • 401 Unauthorized = "너 누구야?" — 신원 자체를 모르겠다. 토큰이 없거나, 만료됐거나, 서명이 깨졌다.
  • 403 Forbidden = "너인 건 알겠는데 안 돼." — 신원은 확인됐지만 권한이 모자란다.

그래서 401은 재시도할 가치가 있고(토큰만 갱신하면 되니까), 403은 없습니다(권한은 갱신으로 안 바뀌니까). installFetchAuth.ts:136이 정확히 그렇게 되어 있습니다 — if (response.status !== 401) return response; 로 401만 골라냅니다.

무한 루프를 막는 장치

401 → 갱신 → 재시도 구조에는 함정이 있습니다. 갱신 후에도 401이 오면? 또 갱신하고, 또 재시도하고… 무한 루프입니다. 이 프로젝트는 두 겹으로 막았습니다. 

// ① 재시도한 요청에 표시를 남김 (installFetchAuth.ts:5, 136)
const RETRY_HEADER = "x-auth-retry";
if (hasRetryMarker(input, init)) return response;   // 이미 재시도했으면 포기

// ② refresh 요청 자체는 절대 재시도 대상이 아님
if (isRefreshRequest(url)) return response;

// ③ 동시에 여러 요청이 401을 받아도 갱신은 한 번만
if (!refreshPromise) {

const refreshed = await refreshPromise;   // 나머지는 이 약속을 같이 기다림

15 — 선택

왜 이걸 골랐고, 안 고른 길은 무엇이었나

지금까지는 "코드가 이렇게 되어 있다"를 설명했습니다. 이 장은 "왜 다른 방법이 아니었나"입니다. 안 고른 길을 알아야 고른 길을 설명할 수 있고, 남의 코드를 읽을 때 비교 기준이 생깁니다.

솔직히 말하면, 이 선택들 중 상당수는 의식적으로 비교한 결과가 아니라 기본값을 따른 것일 겁니다. 그래도 괜찮습니다 — 중요한 건 지금 그 이유를 설명할 수 있느냐입니다.

대안 · 도메인형(패키지 바이 피처)

attendance/ 안에 컨트롤러·서비스·엔티티를 다 넣는 방식. 기능 하나 고칠 때 한 폴더만 열면 됨. 규모가 커질수록 유리.

지금 구조의 대가는 이미 드러났습니다. 출석 기능 하나를 고치려면 controller/, service/, dto/attendance/, entity/, repository/ 다섯 폴더를 오가야 합니다. 다만 dto/는 이미 ai/, crew/, brag/처럼 기능별로 쪼개져 있습니다 — 92개가 되니 견딜 수 없었던 것이고, 규모가 커지면 도메인형으로 기우는 힘을 이 프로젝트 안에서 이미 보여주고 있는 셈입니다.

2. JWT vs 세션

고른 것 · JWT

서버가 아무것도 기억하지 않음(STATELESS). 토큰 안에 신원이 들어 있어 서버를 여러 대로 늘려도 그대로 동작.

대안 · 세션

서버가 로그인 상태를 기억. 즉시 강제 로그아웃이 가능하고 구현이 더 단순. 대신 서버를 늘리면 세션 저장소(Redis 등)가 필요.

JWT의 진짜 대가는 "발급한 토큰을 취소할 수 없다"는 점입니다. 15분짜리 access token은 유출돼도 15분 뒤 죽지만, 그 15분 동안은 서버도 막을 방법이 없습니다. 이 프로젝트가 refresh token만 DB에 저장하는 이유가 여기 있습니다 — revokeAllByUserEmail()로 재발급만은 끊을 수 있게 한 절충안입니다.

3. REST vs GraphQL

엔드포인트 136개는 적은 수가 아닙니다. GraphQL이었다면 하나였겠죠. 그런데 이 프로젝트에는 REST가 맞습니다. {{s4}}장에서 본 출석 응답을 떠올려 보세요 — 출석+이벤트+캐릭터변화를 서버가 알아서 한 번에 묶어 보냅니다. GraphQL의 장점은 클라이언트가 필요한 필드를 직접 고르는 것인데, 여기선 서버가 정해주는 게 오히려 나은 구조입니다. 화면 종류도 36개로 고정이고요.

4. Socket.IO 서버를 따로 vs 백엔드에 통합

고른 것 · 별도 Node 서버

실시간 부하가 REST API에 영향을 안 줌. Socket.IO 생태계가 Node에서 가장 성숙. 따로 껐다 켜도 본체가 안 죽음.

대안 · Spring WebSocket

서버가 하나로 줄어 배포·운영이 단순. 인증을 재사용할 수 있음 — F-01이 애초에 안 생겼을 문제.

F-01(실시간 인증 없음)은 이 선택의 직접적 대가입니다. 서버를 분리하는 순간 인증을 두 번 구현해야 하는데, 그중 하나를 안 한 것이죠. 기술 선택이 어떻게 보안 구멍으로 이어지는지 보여주는 좋은 예입니다. 분리 자체는 합리적이었고, 분리에 따라오는 숙제를 안 한 것이 문제입니다.

5. ddl-auto=update vs Flyway

{{s8}}장에서 다룬 문제입니다. ddl-auto=update는 혼자 빠르게 만들 때 압도적으로 편합니다 — Entity에 필드 하나 추가하면 테이블이 알아서 바뀌니까요. 3월의 폭발적인 개발 속도는 이 선택 덕분이기도 합니다.

대가는 나중에 옵니다. 컬럼 삭제·이름변경이 안 되고, 실제 DB 상태를 아무도 정확히 모르게 됩니다. 그래서 손으로 쓴 SQL이 12개 쌓였고, PostgresSchemaRepairRunner까지 생겼습니다. 속도를 빌려 쓰고 이자를 낸 셈입니다 — 이걸 기술 부채라고 부릅니다.

6. 상태 관리 — React Query만 vs Redux 추가

package.json에는 @tanstack/react-query가 있고 Redux는 직접 의존성에 없습니다(node_modules에 있는 건 다른 패키지가 끌고 온 것). 이건 요즘 기준으로 옳은 선택입니다.

핵심 통찰은 이겁니다 — 이 앱의 상태는 대부분 "서버에 있는 데이터의 사본"입니다. 출석 기록, 캐릭터, 랭킹, 크루… 전부 서버가 진짜 주인이죠. 그런 건 Redux 같은 클라이언트 상태 관리 도구가 다룰 대상이 아니라 캐시의 문제이고, React Query가 정확히 그걸 합니다. staleTime: 30초 한 줄이 Redux 보일러플레이트 수백 줄을 대체합니다.

이 장을 어떻게 쓸까

면접이나 발표에서 "왜 JWT를 쓰셨어요?" 같은 질문이 오면, "JWT는 stateless라서요"는 외운 답입니다. "세션과 비교했을 때 서버 확장이 쉬운 대신 즉시 취소가 안 됩니다. 그래서 저는 refresh token만 DB에 저장해서 재발급은 끊을 수 있게 했습니다" — 이게 이해한 답입니다. 차이는 대가를 말할 수 있느냐에 있습니다.

12 — 균형

그리고 실제로 잘 되어 있는 것들

문제만 나열하면 그림이 왜곡됩니다. 코드를 읽으면서 "이건 제대로 했네" 싶었던 부분도 같은 기준으로 적어둡니다. 발표나 포트폴리오에서 설명할 거리이기도 합니다.

계산을 따로 뗀 게 왜 좋은 설계인가

캐릭터 성장 공식은 service/CharacterGrowthCalculator.java에 131줄로 혼자 들어 있습니다. 이 클래스는 DB를 모르고, HTTP를 모르고, 스프링도 거의 안 씁니다. 숫자를 받아서 숫자를 뱉을 뿐입니다. 

double squatNormalized = normalize(squat / weight, 0.0, 3.0);

// 허벅지 = 스쿼트 70% + 전체 근육량 30%
double quadGrowth = clamp(squatNormalized * 0.7 + muscularityNormalized * 0.3, 0.0, 1.0);

normalize(값, 최소, 최대)는 어떤 수치든 0~1 사이로 눌러 담는 함수입니다. 스쿼트 무게(kg)와 체지방률(%)처럼 단위가 완전히 다른 값을 같은 자로 재기 위한 장치죠. 그리고 squat / weight — 절대 중량이 아니라 자기 몸무게의 몇 배를 드느냐로 평가하므로 체급이 다른 사람끼리도 공정하게 비교됩니다.

이 클래스는 DB 없이 값만 넣어서 테스트할 수 있습니다. "스쿼트 20kg 올리면 다리가 얼마나 굵어지지?"를 서버를 안 켜고 확인할 수 있다는 뜻입니다. 계산과 입출력을 분리하면 이런 게 가능해집니다.

에러 응답이 한 가지 모양으로 통일돼 있습니다

exception/GlobalExceptionHandler.java는 42줄짜리인데 @RestControllerAdvice 하나로 28개 컨트롤러 전체의 예외를 한곳에서 잡습니다. 

@ExceptionHandler(MethodArgumentNotValidException.class)   // 입력값 검증 실패
public ResponseEntity<ApiErrorResponse> handleValidation(...) {
    String msg = e.getBindingResult().getFieldErrors().stream()
            .findFirst().map(fe -> fe.getField() + " " + fe.getDefaultMessage())
            .orElse("Validation error");
    return ResponseEntity.badRequest().body(ApiErrorResponse.builder()
            .status(400).code("BAD_REQUEST").message(msg)
            .timestamp(LocalDateTime.now())
            .path(request.getRequestURI())        // 어느 URL에서 났는지도 기록
            .build());
}

덕분에 프론트엔드는 에러 처리 코드를 한 가지 형태로만 짜면 됩니다. 어느 API를 부르든 실패하면 항상 { status, code, message, timestamp, path }가 오니까요. path를 넣어둔 게 특히 실용적입니다 — 사용자가 에러 화면을 캡처해 보내면 어느 엔드포인트에서 터졌는지 바로 압니다.

스케줄러 — 아무도 안 불러도 도는 코드

scheduler/EventScheduler.java는 21줄입니다. 하는 일은 하나뿐이지만, 웹 서버가 요청에만 반응하는 게 아니라는 걸 보여주는 유일한 예입니다. 

@Scheduled(cron = "0 10 0 * * *", zone = "Asia/Seoul")
public void refreshEventStatuses() {
    eventService.refreshStatusesAndFinalize(LocalDate.now(KST));
}

"0 10 0 * * *"은 매일 0시 10분이라는 뜻입니다 (초 분 시 일 월 요일 순). 정각(0시 0분)이 아니라 10분을 준 게 눈에 띕니다 — 자정에 몰리는 다른 작업들과 겹치지 않게 한 것으로 보입니다. 그리고 zone = "Asia/Seoul"을 명시했습니다. 서버가 해외에 있어도 한국 시간 자정에 돌게 하려는 것이고, 실제로 코드 전체가 ZoneId.of("Asia/Seoul")로 날짜를 다룹니다. 출석 서비스도 마찬가지입니다 — "오늘"의 기준이 흔들리면 출석이 통째로 어긋나니까요.

18 — 실습

층을 진짜로 이해하는 유일한 방법

다이어그램을 백 장 봐도 안 생기는 감각이 있습니다. 필드 하나를 DB에서 화면까지 올려보는 것, 그거 한 번이면 8개 층이 왜 있는지 몸으로 압니다. 각 층에서 같은 데이터가 이름과 모양을 바꾸는 걸 직접 손으로 겪게 되니까요.

과제는 이겁니다 — 출석 기록에 "운동 시간(분)"을 추가한다. 사용자가 오늘 몇 분 운동했는지 입력하고, 그 값이 저장되고, 다시 보이게 만듭니다. 실제 이 프로젝트의 파일과 규칙에 맞춰 썼습니다.

sql · 마이그레이션
DB에 컬럼을 만듭니다

backend/sql/에 기존 파일들과 같은 이름 규칙으로 새로 만듭니다. ddl-auto=update가 자동으로도 해주지만, {{s8}}장에서 본 이유로 기록을 남기는 게 맞습니다. 

-- backend/sql/migration_20260818_attendance_duration.sql
ALTER TABLE attendance_logs
    ADD COLUMN duration_min INT NULL;

NULL을 허용한 게 중요합니다. 이미 쌓인 출석 기록에는 이 값이 없으니까요. NOT NULL로 만들면 기존 데이터 때문에 마이그레이션이 실패합니다.

entity · DB의 모양
AttendanceLog에 필드 추가

자바 필드 이름은 durationMin(카멜), DB 컬럼은 duration_min(스네이크). JPA가 자동 변환하지만 @Column으로 명시하는 게 이 프로젝트 관례입니다. 

// entity/AttendanceLog.java
@Column(name = "duration_min")
private Integer durationMin;      // int가 아니라 Integer — null 가능해야 함

int가 아니라 Integer인 이유: int는 null이 될 수 없어서 값이 없는 기존 기록이 0으로 읽힙니다. "0분 운동함"과 "입력 안 함"은 다른 뜻이죠.

dto · 들어오는 모양
요청 DTO에 필드 추가

사용자가 보내는 값을 받을 자리입니다. 검증도 여기서 붙입니다 — 말이 안 되는 값은 서비스에 닿기 전에 막습니다. 

// dto/attendance/AttendanceUpsertRequest.java
@Min(value = 0,   message = "운동 시간은 0분 이상이어야 합니다")
@Max(value = 1440, message = "운동 시간은 하루를 넘을 수 없습니다")
private Integer durationMin;

여기서 걸리면 GlobalExceptionHandler.handleValidation이 잡아 400 + 저 메시지를 돌려줍니다. {{sERR}}장에서 본 그 경로입니다.

dto · 나가는 모양
응답 DTO에도 추가

들어오는 것과 나가는 것은 다른 클래스입니다. 저장했으면 다시 보여줘야 하니 응답에도 넣습니다. from() 변환 메서드를 잊지 마세요 — 가장 흔한 실수입니다. 

// dto/attendance/AttendanceLogResponse.java
private Integer durationMin;

public static AttendanceLogResponse from(AttendanceLog log, ...) {
    return AttendanceLogResponse.builder()
            .didWorkout(log.isDidWorkout())
            .durationMin(log.getDurationMin())   // ← 이 줄을 빠뜨리면 항상 null
            ...
}

필드만 추가하고 from()을 안 고치면 컴파일은 되고 API도 200을 주는데 값만 null로 옵니다. 에러가 안 나서 찾기 어려운 종류의 버그입니다.

service · 규칙
저장 로직에 반영

AttendanceServiceImpl.java:257의 upsert()에서 신규 생성과 수정 양쪽 다 손봐야 합니다. 한쪽만 고치는 게 흔한 실수입니다. 

// 수정 경로
existing.setDurationMin(request.getDurationMin());

// 신규 생성 경로 (builder)
AttendanceLog log = AttendanceLog.builder()
        .user(user).date(date)
        .durationMin(request.getDurationMin())
        ...

보너스 과제: calculatePointsEarned()에 if (durationMin >= 60) points += 2; 를 넣어보세요. 그러면 이 필드가 게임 시스템에 연결되고, {{s5}}장의 점수 공식을 직접 바꾸는 경험이 됩니다.

controller
대개 고칠 게 없습니다

컨트롤러는 @RequestBody AttendanceUpsertRequest를 통째로 받으므로 DTO에 필드가 늘어난 걸 자동으로 처리합니다. 손댈 필요가 없습니다. 

// controller/AttendanceController.java — 그대로 둠
@PostMapping("/today")
public ResponseEntity<AttendanceLogResponse> upsertToday(
        @AuthenticationPrincipal String email,
        @RequestBody AttendanceUpsertRequest request) { ... }

이게 레이어드 구조의 보상입니다. 데이터가 늘어도 통로는 안 바뀝니다. 여기서 뭘 고쳐야 한다면 설계가 잘못됐다는 신호입니다.

frontend · types
타입에 추가

백엔드가 보내주기 시작해도 TypeScript가 모르면 코드에서 쓸 수 없습니다. 타입 정의에 먼저 추가합니다. 

// frontend/src/types/ (또는 해당 페이지의 타입 선언)
type AttendanceLog = {
  date: string;
  didWorkout: boolean;
  durationMin?: number | null;   // 옵셔널 — 옛 기록엔 없음
};

?와 | null을 붙인 게 2단계의 Integer 선택과 짝을 이룹니다. DB에서 null 가능하면 타입도 그래야 하죠. 이 일관성이 깨지면 런타임에 터집니다.

frontend · 화면
입력창과 표시를 붙입니다

pages/Attendance.tsx에 입력 필드를 넣고, 보낼 때 함께 실어 보냅니다. 토큰은 installFetchAuth가 알아서 붙이니 신경 쓸 필요 없습니다. 

const [durationMin, setDurationMin] = useState<number | "">("");

await fetch("/api/attendance/today", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    didWorkout: true,
    workoutTypes, workoutIntensity, memo,
    durationMin: durationMin === "" ? null : durationMin,
  }),
});

빈 문자열을 null로 바꿔 보내는 처리가 필요합니다. ""를 그대로 보내면 백엔드가 Integer로 파싱하다 400을 뱉습니다.

다 하고 나면

파일 7개를 고쳤고, 그중 컨트롤러만 안 고쳤습니다. 그리고 같은 데이터가 이름을 네 번 바꿨습니다 — duration_min(DB) → durationMin(Entity) → durationMin(DTO) → durationMin(JSON) → durationMin(TS).

"왜 이렇게 번거롭지?"라는 생각이 들었다면 정상입니다. 그게 레이어드 구조의 비용이고, {{sALT}}장에서 도메인형 대안을 얘기한 이유이기도 합니다. 대신 각 층이 자기 관심사만 신경 쓴다는 보상이 있습니다 — DB는 null을, DTO는 검증을, 화면은 표시를.

수정할 땐 저장이 안 됨5단계에서 신규 생성 경로만 고침

이 표가 곧 레이어드 구조의 디버깅 지도입니다. 증상만 보고 어느 층인지 짚을 수 있으면, 이 프로젝트는 이미 네 것입니다.

일부러 고장 내보기 — 6가지 실험

제일 빨리 배우는 방법은 하나씩 꺼보는 것입니다. 각 실험은 이 문서의 어느 부분을 증명하는지 함께 적었습니다.

실험예상되는 증상증명하는 것
realtime 서버만 끄기 다른 기능은 멀쩡한데 라운지만 안 됨 세 프로그램이 정말 독립적이라는 것
백엔드만 끄기 화면은 뜨는데 데이터가 전부 빔 프론트엔드는 데이터를 갖고 있지 않다는 것
개발자도구 → Application → localStorage에서 user 삭제 후 새로고침 로그인 화면으로 튕김 세션이 localStorage에 의존한다는 것 (F-03의 근거)
localStorage의 role을 ROLE_ADMIN으로 고치고 /admin 접속 화면은 잠깐 열리지만 데이터가 안 옴 / 튕김 프론트 가드는 뚫려도 서버는 안 뚫린다 — 가장 중요한 실험
Network 탭 켜고 출석 체크 요청 한 번에 출석+이벤트+캐릭터변화가 전부 응답에 옴 응답 설계(한 번에 보내기)의 실제 효과
인바디 사진 대신 아무 사진이나 업로드 경고 문구가 붙은 결과가 나오거나 실패 AI 품질 검사가 실제로 동작한다는 것

네 번째 실험을 꼭 해보세요

브라우저에서 자기 역할을 ADMIN으로 바꿔도 관리자 데이터가 안 나오는 걸 직접 보는 것 — 이게 "클라이언트를 절대 믿지 않는다"는 원칙을 몸으로 이해하는 가장 빠른 방법입니다. 서버는 localStorage를 쳐다보지도 않고, JWT 안에 서명된 role만 봅니다.

어디서 막혔는지 찾는 순서

문제가 생겼을 때 이 순서대로 확인하면 대부분 3분 안에 원인이 나옵니다.

  1. 브라우저 개발자도구 → Network 탭. 요청이 나가긴 했나? 상태 코드가 뭔가?
  2. 401이면 → 인증 문제. 토큰이 안 붙었거나 만료. Authorization 헤더를 확인.
  3. 403이면 → 권한 문제. 로그인은 됐는데 role이 부족한 것. SecurityConfig에서 그 URL 규칙을 찾아보세요.
  4. 404면 → URL 오타이거나 컨트롤러에 그 매핑이 없는 것.
  5. CORS 에러면 → 백엔드의 cors.allowed-origins에 localhost:5173이 있는지.
  6. 요청 자체가 안 나갔으면 → 프론트엔드 코드 문제. Console 탭의 빨간 에러부터.
  7. 백엔드 터미널 로그를 보세요. 예외 스택트레이스가 원인을 그대로 말해줍니다.

이 프로젝트에는 dev.out.log와 dev.err.log가 루트에 남아 있습니다. 예전에 이렇게 디버깅한 흔적이겠죠.

이 문서를 다 이해했는지 확인하는 질문 7개

막힘없이 답할 수 있으면 이 프로젝트를 설명할 준비가 된 겁니다.

  1. 출석 기록은 DB에 저장하는데 라운지 위치는 왜 저장하지 않나?
  2. Entity를 그대로 API 응답으로 내보내면 무슨 일이 벌어지나?
  3. 매일 출석만 열심히 하면 캐릭터 티어가 오르나? 왜 안 오르나?
  4. OpenAI API 키가 브라우저에 노출되지 않는 이유는?
  5. 브라우저에서 내 역할을 ADMIN으로 바꾸면 관리자 페이지를 쓸 수 있나?
  6. AI가 인바디 숫자를 잘못 읽었을 때 코드는 어떻게 알아채나?
  7. @Transactional이 없으면 출석 체크에서 무슨 문제가 생길 수 있나?

00 — 문제집

풀면서 배우는 CS

앞의 퀴즈가 진단이었다면 여기는 훈련입니다. 기술 영역 8개로 묶었고, 각 영역마다 같은 흐름으로 갑니다 — 개념을 아는지(객관식) → 이 프로젝트에선 어떻게 쓰였는지(단답) → 그래서 뭐가 좋아졌는지(서술형).

해설은 정답만 알려주지 않고 헷갈리는 개념을 구분하는 데 집중했습니다. 스로틀링과 디바운싱, 해시와 암호화, 인증과 인가 — CS 실력은 이런 경계를 아는 데서 늘어납니다.

서술형은 자동 채점이 불가능하니 직접 써본 뒤 채점 포인트로 자가채점합니다. 모범답안만 읽는 것보다, 내 답에 뭐가 빠졌는지 찾는 쪽이 훨씬 남습니다.
