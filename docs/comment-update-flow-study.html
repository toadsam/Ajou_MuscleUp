코드를 닫고 먼저 답해 보기

1. 프론트에서 수정 버튼을 숨기는데 서버에서도 권한을 검사하는 이유는?

브라우저 화면은 사용자가 바꿀 수 있고 API를 직접 호출할 수도 있습니다. 실제 보안 경계는 서버이므로 댓글 작성자 ID를 서버에서 다시 확인해야 합니다.

2. 토큰이 만료됐는데 사용자가 곧바로 로그인 화면으로 가지 않을 수 있는 이유는?

앱 시작 시 설치된 전역 fetch가 401을 가로채 Refresh Token으로 Access Token을 재발급하고 원래 PATCH 요청을 한 번 다시 보내기 때문입니다.

3. SecurityConfig 검사와 Service 검사의 차이는?

SecurityConfig는 USER·ADMIN이 댓글 API에 들어올 수 있는지 검사합니다. Service는 들어온 사용자가 그 댓글의 작성자이거나 관리자인지 검사합니다.

4. findById로 가져온 댓글에서 save를 빼도 수정될 수 있는 이유는?

@Transactional 안에서 조회한 엔티티는 영속성 컨텍스트가 관리합니다. 필드가 바뀌면 트랜잭션 종료 시 Hibernate 변경 감지가 UPDATE를 만들 수 있습니다.

5. 수정 성공 후 댓글 목록을 다시 요청하지 않아도 화면이 바뀌는 이유는?

서버가 돌려준 수정 댓글을 이용해 React의 comments 배열에서 ID가 같은 항목 하나만 교체하기 때문입니다.

30초 설명 기준

댓글 저장 시 React가 PATCH 요청을 보냅니다. 전역 fetch가 Access Token을 붙이고, 만료됐다면 한 번만 재발급한 뒤 재시도합니다. 서버의 JWT 필터가 이메일과 역할을 SecurityContext에 넣고, SecurityConfig가 USER·ADMIN의 API 진입을 허용합니다. Controller가 URL·JSON을 Java 값으로 바꾸고, Service가 DB 사용자와 댓글 작성자를 비교합니다. 본인이나 관리자면 트랜잭션 안에서 내용을 바꾸고 DTO를 반환하며, 프론트는 받은 댓글 하나만 화면 상태에서 교체합니다.
